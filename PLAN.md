## 1. Approach in one paragraph

**Test the riskiest assumption first, then build the spine, then hang the scenarios on
it.**

1. **Week 1 (M1)** answers the question that could change the project's shape: does
   TrustGraph run on the author's machine, with a local LLM and the decision models,
   well enough to extract the synthetic persona's facts? If not, we switch to fixture
   facts for v0.4 and say so.
2. **The spine (M2)** is the gate and the ledger. Every scenario depends on them, and
   S4 (the hostile counterparty) needs nothing else, so it proves them.
3. **The negotiation (M3)** reuses the deterministic Neocloud engine and needs no
   TrustGraph, so it cannot be blocked by M1.
4. **Belief and consent (M4)** bring TrustGraph in fully for S1, and S2 if time allows.
5. **Release (M5)** publishes the report and recorded runs.

Everything is local and containerised, with no npm runtime dependencies. Each outside
connection sits behind an adapter so external services can be added later.

## 2. Technical decisions

| # | Decision | Chosen option | Why | Alternatives rejected |
| --- | --- | --- | --- | --- |
| D-01 | Hosting (site) | GitHub Pages via Actions (live since 2026-11-25) | Free, already set up | Netlify, Vercel |
| D-02 | Language | JavaScript (ES modules) on Node.js ≥ 20, **standard library only** | Reuses the Neocloud engine as is; the same code runs in the browser for site replays; Node has SHA-256 and Ed25519 built in; no supply-chain surface | Python (TrustGraph's SDK is Python, but its REST and WebSocket APIs suffice); TypeScript (adds a build step; revisit after v0.4) |
| D-03 | Container runtime | Docker Compose. TrustGraph's compose file is generated by `npx @trustgraph/config`; Wayfinder's own compose file joins it through a shared network. | One command to start; follows TrustGraph's supported path | Kubernetes / Minikube (heavier); Podman (should work; not tested) |
| D-04 | Sandbox | The agent container sits on a Docker `internal: true` network shared **only** with the gate. The gate is also on the backend network with TrustGraph, Ollama and the ledger volume. | "No side door" is enforced by the network, not by trusting the agent (FR-13) | Agent configuration alone; firewall rules on the host |
| D-05 | Agent ↔ gate | MCP (JSON-RPC 2.0) over HTTP: the minimal subset `initialize`, `tools/list` and `tools/call`, implemented on the Node standard library | Keeps the gate replaceable and lets a general MCP agent connect later (US-19) | Custom REST API (non-standard); the official MCP SDK (a dependency; this is the fallback if interoperability fails, OQ-05) |
| D-06 | Ledger format | JSONL per run. Canonical JSON in the style of RFC 8785; numbers restricted to integers, with decimals stored as strings so canonicalisation stays simple. `entryHash = SHA-256("wayfinder-ledger-v1" ‖ 0x00 ‖ canonical)`; Ed25519 signature. | Follows the Agentic Language Development design; portable; streams well | SQLite (adds a native dependency; revisit if runs grow, Q15) |
| D-07 | Keys and head commitments | Generated locally on first run into `~/.wayfinder/keys/`, which only the gate container mounts (read-only). Head commitments go to `~/.wayfinder/heads/`, outside the run directories. Test mode uses fixed test keys stored under `test/keys/` and marked "test only". | Keys never reach the agent or the repository; the head commitment is held apart from the ledger (A-15) | Keys in the repository; keys in environment variables |
| D-08 | Knowledge store | TrustGraph v2.11, one workspace for the persona. Ontology authored in Turtle under `ontology/` and converted to TrustGraph's ontology configuration if needed (OQ-03). | TrustGraph is the project's foundation; Turtle is the portable source | A bespoke triple store |
| D-09 | LLM | Ollama in a container. The model is chosen in M1 by A-01 on F-P within the hardware, and pinned by tag and digest. | Local, free, and supported by TrustGraph | Hosted APIs (excluded in v0.4; possible later through TrustGraph's providers) |
| D-10 | Decision models | TrustGraph's decision-scoring (Laya) and Cloze services, called by the gate. Advisory only (FR-15, FR-18). | Fast, local, no prose parsing | LLM prompts for yes/no decisions (slow and brittle) |
| D-11 | Negotiation engine | Vendor `docs/assets/js/nego/*` and `lib/rng.js` from Neocloud Supply OS at [`96a6161`](https://github.com/yorkerhodes3/neocloud-supply-os/commit/96a6161c6d2b) into `vendor/neocloud-nego/`, keeping its LICENSE and NOTICE. Add two lease scenarios in its scenario format. Wrap moves so that every offer passes the gate. | Deterministic, tested (88 tests in its repository), already models mandates, escalation, tactics and seat redaction | Rewrite; the DTSF TypeScript twins (heavier; contract mode unbuilt) |
| D-12 | Contract clauses | A small module implementing the state machine in FR-33, following the DTSF Gate 5 rules | DTSF's contract mode is not built (501 stubs) | Waiting for DTSF |
| D-13 | Readout and seat view | Static HTML and plain text generated from the ledger by a Node script, using the site's CSS approach | No framework; works offline and on Pages | A web app |
| D-14 | Testing | `node:test`. Unit tests for gate, ledger, clauses and the mandate form. The harness produces the A-ID report. CI runs unit tests plus S3, S4 and the ledger trials in test mode (no TrustGraph needed). S1 and S2 run locally. | Zero dependencies; CI covers everything that does not need the local models | Jest or Vitest (dependencies) |
| D-15 | The agent | A scenario agent (scripted steps, plus an adversarial mode) in its own container. TrustGraph's agent orchestrator through the gate is the stretch goal (US-19). | Tests target the gate and ledger, which must hold whatever the agent does | Building an agent framework (out of scope) |
| D-16 | Adapters | Interfaces for: LLM provider, decision models, counterparty transport, identity / trust list, ledger anchoring, world data. v0.4 ships the local implementations only. | Honours "don't make assumptions that prevent external dependencies" | Hard-wiring local services |

## 3. Architecture

```text
 ┌──────────── wf-sandbox (internal: no internet) ───────────┐
 │  agent (scenario agent) ──MCP/HTTP──► gate                  │
 └──────────────────────────────────────┬──────────────────────┘
                                        │ wf-backend
        ┌───────────────┬───────────────┼──────────────────┬───────────────────┐
        ▼               ▼               ▼                  ▼                   ▼
  TrustGraph       Ollama (LLM)   Decision models    Tool adapters        Ledger writer
  (compose from    pinned model   (TrustGraph:       hotel fixture,       JSONL + Ed25519
  @trustgraph/                    Laya, Cloze)       negotiation room,    → runs/<id>/ledger.jsonl
  config)                                            counterparty stand-   heads → ~/.wayfinder/heads
                                                     ins, commit stubs
```

**Components:**

| Component | Responsibility | Notes |
| --- | --- | --- |
| Gate | MCP server; rule evaluation (precedence in FR-15); read filtering; approvals; dispatch with idempotency; signals | The only component holding tool credentials and the ledger key |
| Ledger writer | Append, hash, sign; seal; head commitment; dispatch log | In-process with the gate; writes before dispatch (FR-14) |
| Quarantined reader | Parses counterparty content into typed fields; keeps free text as display-only | Has no tools; runs inside the gate's process boundary but has no access to the tool registry |
| Scenario agent | Runs scenario scripts and the adversarial mode | Container on `wf-sandbox` only |
| Negotiation room adapter | Drives the vendored engine; routes every move through the gate | Counterparty agents are engine seats |
| Clause module | FR-33 state machine | |
| Mandate form | CLI questionnaire → signed mandate | FR-28 |
| Readout / seat view / why | Generated outputs | FR-34–FR-36 |
| Harness | Runs scenarios and trials; writes the A-ID report | FR-37 |
| `wf` CLI | Person's interface | §6.1 of the spec |

## 6. Sequence and dependencies

```text
M0 ──► M1 ──► M2 ──► M3 ──► M4 ──► M5
              │              ▲
              └── M3 does not need M1's outcome (no TrustGraph in S3)
```

- **M1 before everything** because its outcome decides between live and fixture
  extraction for S1 and S2.
- **M2 blocks M3 and M4:** every offer, read and disclosure goes through the gate and
  onto the ledger.
- **M3 before M4:** S3 is the author's priority and does not depend on TrustGraph, so a
  bad M1 outcome cannot stall it.
- **External things to get early:**
  - Docker installed with enough disk space for the TrustGraph images and a model (check
    on day 1);
  - the model weights pulled before week 1 ends.

## 8. Quality bar

- **Definition of ready:** a backlog item has Given/When/Then acceptance criteria and
  references an `FR-xx` or `A-xx` (or is marked infrastructure).
- **Definition of done (per item):**
  - implemented and self-tested against its criteria;
  - unit tests added where it has logic;
  - the harness is still green for the A-IDs it touches;
  - reviewed and merged through a pull request;
  - BACKLOG updated.
- **Testing:**
  - Automatic: unit tests, S3, S4, ledger trials, and the determinism check (FR-38).
  - Local only: S1 and S2 (need TrustGraph and models).
  - Manual: A-17.
- **Review:** every change goes through a pull request; AI-generated code is read line
  by line before merge.
- **Honesty:** the harness may report `not measured`, but never a `pass` it did not
  measure.

## 11. What we will do if we run out of time

Cut in this order, decided now:

1. Cut the A-18 baseline (A-18 reported as `not measured`).
2. Cut S2 (A-06 `not measured`).
3. Cut decision-model signals; rules alone still decide (FR-18 becomes "Later").
4. Cut live extraction and use fixtures (A-01 `not measured`, FR-04).
5. Cut the HTML readout and ship the plain-text readout only (FR-34, partial).
6. Ship recorded runs without the site page; link them from the README.

Never cut: the gate, the ledger's integrity checks, fail-closed behaviour, hard bans, or
"only the person agrees".
